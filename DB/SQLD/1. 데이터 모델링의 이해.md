
## 1. 데이터 모델의 이해 

### 모델링 정의 
- 복잡한 개념을  일정한 `표기법`으로 나타내는 것 
	- ERD, UML class Diagram, UML Sequence Diagram 등 
- 사물 또는 사건에 대한 관점, 양상을 명확히 하는 것 
- 모델 : 현실 세계의 추상화된 반영 

### 모델링의 특징 
- 추상화 (모형화, 가설적) : 복잡한 것을 일정 형식에 따라 표현
- 단순화 : 난해한 개념을 약속된 표현으로 쉽게 이해할 수 있게 함
- 명확화 : 누구나 이해할 수 있게 모호함을 배제
- 정보시스템 구축 : 계획, 분석, 설계 - 업무 분석 및 설계 -> 구축/운영 단계 - 변경과 관리의 목적으로 이용 (데이터 모델링은 계획, 설계뿐만 아니라 구축/운영 시에도 사용됨

### 데이터 모델링의 3요소 
- thing (Entity) : 관리하고 싶은 대상/개념 (회원, 주문)
- Attributes (속성) : 그 대상을 설명하는 특성/정보 (회원의 이름, 이메일, 주문의 일시, 금액)
- Relationship  (관계) : Thing 과 Thing의 관계 

### 모델링의 3가지 관점 
- 데이터 관점 What : 업무와 데이터 또는 데이터 간의 관련성 
	- 회원, 상품, 주문, 주문상세와 같은 데이터가 있고 서로 어떤 관계인지 보는 것 
	- 회원 1 - N 주문 
	- 주문 1 - N 주문 상세 
	- 상품 1 - N 주문 상세 
- 프로세스 관점 How : 실제 업무는 무엇인지 또는 해야 하는 일을 모델링 
	- 상품조회 -> 주문 생성 -> 결제 -> 배송 -> 주문 완료 
- 데이터와 프로세스의 상관 관점 : 작업 방법에 따라 어떤 영향을 받는지 모델링 
	- Process 결제 성공 -> data order.status 변경, Payment INSERT, Stock.quantity UPDATE  

### 데이터모델링 유의사항 
- 중복 (Duplication) : 여러 장소에 같은 정보를 저장하는 잘못 
- 비유연성(Inflexibility) : 유지보수의 어려움 
- 비일관성 (Incinsistency) : 데이터 간 상호 관계에 대한 명확한 정의를 하지 않을 경우, 프로세스가 진행 중 데이터가 일치하지 않을 수 있음 

### 데이터모델링 과정
- **개념적 데이터 모델링 :** 
  `추상화 수준이 높고`, 업무 중심적, 포괄적인 수준의 모델링, 전사적 데이터 모델링 
- **논리적 데이터 모델링 :** 
  시스템을 구축하고자하는 업무에 대해 key, 속성, 관계 등을 정확하게 표현, `재사용성 높음` 
- **물리적 데이터 모델링 :** 
  실제로 데이터베이스에 이식할 수 있도록 성능, 저장 등 `물리적인 성격을 고려하여 설계` 

### 데이터베이스 스키마 구조3단계 
- 외부 스키마
	- View 단계 여러개의 사용자 관점으로 구성 
	- 사용자 단계로서 사용자가 보는 개인적 DB 스키마 
	- DB의 사용자나 응용 프로그래머가 접근하는 DB정의 
	> `사용자관점`, 접근하는 특성에 따른 스키마 구성
- 개념 스키마
	- 모든 사용자 관점을 통합한 조직 전체의 DB를 기술 
	- 모든 응용 시스템들이나 사용자들이 필요로 하는 데이터를 통합한 조직 전체의 DB 기술
	- DB에 저장되는 데이터와 그들간의 관계를 표현하는 스키마 
	> `통합 관점`
- 내부 스키마
	- DB가 물리적으로 저장된 형식 
	- 물리적 장치에서 데이터가 실제적으로 저장되는 방법을 표현하는 스키마
	> 물리적 저장구조 

> 데이터 베이스를 구축하기 전, 데이터를 어떤 방식으로 풀어낼까? 고민하고 도출하는 방법, 
> 즉, 어떤 서비스를 위한 데이터들의 관계, 속성을 ERD, UML로 표기하기 위한 과정 

### 성능 데이터 모델링
데이터베이스 성능을 향상 시키기 위해 설계 단계부터 성능과 관련된 사항들이 모델링에 반영되는 것
- 데이터 모델에 맞게 정규화 수행
- DB용량 및 트랜잭션 유형을 파악하여 성능 저하를 일으키는 부분이 없는지 검토 
- 용량과 트랜잭션 유형에 맞게 반정규화 수행
- 성능 향상을 위한 PK/FK 조정, 이력 몯레 조정, 슈퍼/서브타입 조정 등 수행
- 데이터모델의 성능 검증

## ERD 
데이터 모델에 대한 표기법 `1976년 피터첸`이 Entity-Relationship model이라는 표기법을 만듦 

### ERD 작성 순서
1. 엔티티 작성
2. 엔티티를 적절하게 배치 
3. 엔티티간 관계 설정 
4. 관계명을 기술
5. 관계의 참여도 기술
6. 관계의 필수 여부 기술 

### 엔티티, 인스턴스, 속성, 속성값의 관계 
![[Pasted image 20260809174452.png]]

#### 엔티티 :  필요하고 유용한 정보를 저장하고 관리하기 위한 집합적인 것(Thing)
- 두 개 이상의 인스턴스의 집합 
- 두 개 이상의 속성을 가짐
- 하나의 인스턴스에서 각각의 속성은 한 개의 속성값을 가짐 

특징 
-  반드시 해당 업무에서 필요하고 관리하고자 하는 정보이어야 함 
- 유일한 식별자에 의해 식별할 수 있어야 함 
- 영속적으로 존재하는 인스턴스의 집합이어야함 
- 엔티티는 업무 프로세서에 의해 이용되어야 함 
- 엔티티는 반드시 속성이 있어야 함 
- 엔티티는 다른 엔티티와 최소 한개 이상의 관계가 있어야 함 

##### 발생시점에 따른 엔티티 분류 

기본 엔티티 (Fundanmental Entity) / 키 엔티티(Key Entity)
- 그 업무에 원래 존재하는 정보로서 다른 엔티티와 관계에 의해 생성되지 않고, `독립`적으로 생성이 가능하고 자신은 타 엔티티의 부모의 역할을 하게 됨 
- 다른 엔티티로부터 주 식별자를 상속 받지 않고 고유한 주 식별자를 가지게 된다 
- 사원, 부서, 고객, 상품, 자재 등 

중심엔티티(Main Entity) 
- 기본 엔티티로부터 발생
- 업무에 있어서 중심적인 역할
- 데이터의 양이 많이 발생
- 다른 엔티티와 관계를 통해 많은 행위 엔티티 생성 
- 계약, 사고, 예금, 원장, 청구, 주문, 매출 등 

행위 엔티티 (Active Entity)
- 두개 이상의 부모 엔티티로부터 발생
- 자주 내용이 바뀌거나 데이터량이 증가 
- 분석 초기 단계에는 잘 나타나지 않으며 상세 설계단계나 프로세스와 상관 모델링을 진행하면서 도출 될 수 있음 
- 주문 목록, 사원 변경이력 등 

#### 속성 
업무에 필요로 하는 인스턴스로 관리하고자 하는 더 이상 분리되지 않은 최소 데이터 단위 

- 해당 업무에서 사용하는 이름을 부여
- 서술식 속성명은 사용하지 않음 
- 약어 사용은 가급적 제한 
- 전체 데이터 모델에서 유일성을 확보하는 것이 좋음 (반정규화, 통합 등의 작업에서 혼란을 방지할 수 있음)

##### 속성의 특성에 따른 분류 
- 기본 속성 : 업무분석을 통해 바로 정의한 속성을 기본 속성 ( 원금, 예치기간, 이자율)
- 설계 속성 : 원래 업무상 존재하지는 않지만, 설계를 하면서 도출해내는 속성 (예금 분류)
- 파생 속성 : 다른 속성으로부터 계산이나 변형이 되어 생성되는 속성 (이자)

#### 도메인 
각 속성이 가질 수 있는 값의 범위
엔티티 내에서 속성에 대한 데이터 타입과 크기 , 제약사항을 지정 

#### 관계 
분류 
- 관계는 `존재에 의한 관계`와 `행위에 대한 관계`로 구분될 수 있음
- UML에는 클래스 다이어그램의 관계 중 연관관계 (Association)와 의존 관계 (Dependency)가 있고, 이것을 구분하여 연관관계는 `실선`, 의존 관계는 `점선`으로 표현 
- ERD에서 `존재적 관계`와 `행위에 의한 관계`룰 구분하지 않고 단일화된 표기법을 사용 

표기법 
- 관계명(Membership) : 관계의 이름
- 관계차수(Cardinality)  : `1:1`, `1:M` , `M:N`
- 선택사항(Optionality) : 필수관계, 선택관계 

체크사항 
- 두 개의 엔티티 사이에 관심있는 연관 규칙이 존재하는가? 
- 두 개의 엔티티 사이에 정보의 조합이 발생되는가? 
- 업무기술서, 장표에 관계연결에 대한 규칙이 서술되어 있는가? 
- 업무기술서, 장표에 관계연결을 가능하게 하는 동사가 있는가? 

관계 읽기 
- 기준(Source) 엔티티를 한개(One) 또는 각(Each)으로 읽는다
- 대상(Target) 엔티티의 관계참여도 즉 개수(하나, 하나 이상)를 읽는다. 
- 관계 선택사양과 관계명을 읽는다. 

### 식별자 
각 인스턴스를 구분하게 만들어주는 대표적인 속성 

#### 주 식별자 (PK)의 속성
PK (Primary Key) 기본키, 주식별자라고 불림
하나의 속성이 주 식별자가 될 수도 있고, 여러개의 속성이 주 식별자가 될 수도 있음 

- 유일성 : 각 인스턴스에 유니크함을 부여해서 식별 가능하도록 한다
- 최소성 : 유일성을 보장하는 최소 개수의 속성이어야 함 
- 불변성 : 속성값이 되도록 변하지 않아야 함 
- 준재성 : 속성값이 null일 될 수 없음 

#### 식별자의 분류 

**대표성 여부**
- 주 식별자 :
	- 유일성, 최소성, 불변성, 존재성을 가진 대표 식별자 
	- 다른 엔티티와 `참조관계`로 연결 
- 보조 식별자 : 
	- 인스턴스를 식별할 수는 있지만, 참조 관계 연결 X 
	- 다른 엔티티와 참조 관계 X 

**스스로 생성되었는지 여부**
- 내부 식별자 : 엔티티 내부에서 스스로 생성된 식별자 
- 외부 식별자 : 다른 엔티티에서 온 생성자, 다른 엔티티와의 연결고리 역할 FK 

**단일 속성의 여부** 
- 단일 식별자 : 하나의 속성으로 구성된 식별자 
- 복합 식별자 : 두개 이상의 속성으로 구성된 식별자 

**대체여부**
- 원조 식별자 : 업무 프로세스에 존재하는 식별자 (가공되지 않은 우너래의 식별자)
- 대리 식별자 : 주 식별자의 속성이 두 개 이상인 경우, 그 속성들을 하나로 묶어서 사용하는 식별자 (두개를 묶어서 만들어냄)

#### 식별자 VS 비식별자 

식별자 관계 
- 자식 엔티티에 PK가 따로 없고, 다른 엔티티의 PK를 FK로 사용 
- 부모 엔티티에 있어야 자식 엔티티를 생성할 수 있음 (1:1, 1: N)

비식별자 관계
- 부모 엔티티의 식별자가 자식 엔티티의 일반 속성이 되는 관계
- 부모 엔티티가 없어도 자식 엔티티를 생성할 수 있고, 부모 엔티티가 삭제되어도 자식 엔티티가 존재할 수 있음

## 정규화 
정규화는 데이터 정합성 (데이터의 정확성과 일관성을 유지 보장)을 위해 
`엔티티를 작은 단위로 분리하는 과정`

### 제 1 정규화 
하나의 속성은 반드시 하나의 값만 가져야 함
*취미라는 컬럼에 농구, 영화감상, 클라이밍 과 같이 여러 개의 앖이 들어가면 안됨*

![[Pasted image 20260816235011.png]]

### 제 2 정규화 
인티티의 모든 일반 속성은 만드시 `모든 주식별자`에 종속되어야 한다
주 식별자가 단일 식별자가 아닌 복합 식별자일 경우 제 2정규를 통해 테이블을 분리한다 

### 제 3 정규화 
주 식별자가 아닌 모든 속성 간에는 서로 종속될 수 없다. 
*이행적 함수 종석성을 제거*
#### 3 정규화 예시 
주문번호 → 고객ID
고객ID → 고객명, 고객등급

주문 테이블

| 주문번호(PK) | 고객ID | 고객명 | 고객등급 |
| -------- | ---- | --- | ---- |
| 1001     | C01  | 민수  | GOLD |
| 1002     | C02  | 지수  | VIP  |

정규화 후

 주문 테이블

| 주문번호(PK) | 고객ID(FK) |
| -------- | -------- |
| 1001     | C01      |
| 1002     | C02      |

 고객 테이블

| 고객ID(PK) | 고객명 | 고객등급 |
| -------- | --- | ---- |
| C01      | 민수  | GOLD |
| C02      | 지수  | VIP  |

### 반정규화 
데이터의 조회 성능을 향상 시키기 위해 `데이터의 중복을 허용하거나`, `데이터를 그룹핑하는 과정`
- 조회 성능 향상 가능성
- 입력, 수정, 삭제 성능 저하 가능성
- 데이터 정합성 문제 발생 가능성
- 반정규화는 반드시 정규화 과정이 끝난 후 진행 

#### 테이블 병합
업무 프로세스 상 join이 많이 발생하는 경우, 테이블을 병합 하는 것이 성능 측면에서 유리할 경우 테이블 병합 고려 

1:1 관계 테이블 병합 
- 1:1 관계를 맺고 있는 테이블을 하나의 PK를 갖는 테이블로 병함

1:N 관계 테이블 병합 
1:N의 관계를 맺고 있지만, 항상 같이 조회되어 join이 많이 발생하는 경우, 테이블 병합을 고려할 수 있음 
단, 테이블은 병합되어도 일부 요소에 대해서는 중복 데이터가 발생할 수 있음 

#### 테이블 분활
- 수직 분할 : 엔티티의 일부 속성을 별도의 엔티티로 분할 (1:1 관계 성립 )
- 수평 분할 : 엔티티의 일부 속성을 별도의 엔티티로 분할 (DB 파티셔닝) 
  *주문 일자 컬럼을 기준으로 연도별로 테이블을 분리할 수 있음*
- 테이블 추가 
	- `중복 테이블` 추가 : 데이터의 중복을 감안하더라도 성능상 반드시 필요하다고 판단되는 경우 별도의 엔티티 추가 
	- `통계 테이블` 추가 : 여러 엔티티를 조회하여 통계를 <U>계산할 일이 많은 경우 미리 계산하여 엔티티로 저장</U>
	- `이력테이블`추가 : 과거 이력을 저장해야 하는 경우, 별도 엔티티 추가 
	- `부분 테이블`추가 : 특정 프로세스를 진행 시에 특정 속성에 대한 조회가 다량으로 발생하는 경우, <U> 프로세스에 필요한 정보만 부분 테이블로 추가 </U>
#### 컬럼 반정규화 
- `중복 컬럼`추가 : 컬럼을 추가하는 것이 유리할 경우 
- `파생 컬럼`추가 : 프로세스 수행 시 부하가 염려되는 계산 값을 미리 컬럼으로 저장하여 보관하는 방식 
- `이력 테이블 컬럼` 추가 : 대량의 이력 테이블을 조회하는 경우, 조회 기준이 될만한 컬럼을 미리 추가해놓는 방식 

#### 관계 정규화 
중복 관계를 추가하는 것이 성능 측면에서 유리할 경우 추가 

## 트랜잭션
데이터를 조작하기 위한 하나의 논리적인 작업 단위 

### 트랜잭션 ACID 속성 
원자성 (Atomicity) 
- 트랜잭션 내에서 실행한 작업들은 마치 하나의 작업인 것 처럼 모두 성공 or 모두 실패 
- 모두 성공 시에는 커밋, 실패 시 롤백 

일관성 (Consistency)
- 모든 트랜잭션은 일관성 있는 데이터베이스 상태를 유지해야 함
- 데이터베이스에서 정한 무결성 제약 조건을 항상 만족해야 함 
- 무결성 제약 조건 : DB가 미리 정해둔 데이터 규칙, 이메일 중복 불가, 나이는 0 이상 등 

격리성 (Isolation)
- 동시에 실행되는 트랜잭션들이 서로에게 영향을 미치면 안됨 
- 동시 데이터 수정 등을 금함 

영속성(Durability)
- 트랜잭션을 성공 적으로 끝내면 그 결과가 항상 기록되어야 함 
- 중간 시스템에 문제가 발생해도 데이터베이스 로그등을 사용하여, 성공한 트랜잭션 내용을 `복구`해야함

**커넥션**
사용자는 `WAS`,DB 접근 툴 등의 클라이언트를 사용해서 DB서버에 접근할 수 있다.
그러면 클라이언트는 데이터베이스 서버에 연결을 요청하고 커넥션을 맺는다
이 때, DB 서버는 내부에 세션을 만들어 세션을 통해 커넥션을 통한 요청을 실행한다

**세션**
트랜잭션 기능을 사용 시 세션 내에서 동작, 하나의 세션 내에서 커밋, 롤백을 하고 세션을 종료 
- 커밋한다면 세션 종료 후 데이터베이스 결과 반영
- 롤백 시 세션 시작 이전으로 되돌림 
*세션 != 트랜잭션 => 세션이 더 큰 작업 공간 + 연결 단위*
하나의 세션에서 트랜잭션 여러 번 가능

- 기본적으로 데이터베이스는 자동커밋으로 설정돼 있음 -> 쿼리 실행 시 즉각적으로 데이터베이스에 반영 
*자동 커밋을 해제하고 수동 커밋 모드로 변경하는것이 트랜잭션의 시작*

```SQL
set autocommit false; // 수동 커밋모드 설정

```

2. 쿼리 실행 
3. 커밋, 롤백

## Null 값 처리 

### 가로 연산에서 Null 처리
가로 연산 (하나의 row에서의 값 처리)의 경우 Null이 포함돼 있으면, 해당 결과값은 Null이 된다.
예 ) User A의 `수입` - `지출`을 계산하는 과정 *수입, 지출은 하나의 인스턴스의 다른 컬럼*
### 세로 연산에서 Null 처리 
세로연산(다른 인스턴스의 데이터와 연산)의 경우 Null값을 그냥 제외 한다. 
예 ) UserA의 `수입`과 UserB의 `수입`을 더하는 경우
