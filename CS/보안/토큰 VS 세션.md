## 세션 기반 인증 
![[Pasted image 20260108023905.png]]
서버가 사용자의 상태를 관리하는 방식
- 사용자가 로그인하면 서버는 `세션 ID`를 생성하고 이를 클라이언트에 `쿠키`로 전달
- 클라이언트는 이후 요청 시 `세션 ID`를 포함하여 서버에 전달하며, 서버는 이를 기반으로 사용자의 상태를 확인

<장점>
- 세션 기반 인증은 상태를 서버에 저장하기 때문에 사용자의 상태를 쉽게 관리할 수 있음

<단점>
- 서버의 메모리를 많이 소모
- 대규모 트래픽 환경에서는 확장성이 떨어질 수 있음
- 모바일 환경에서는 쿠키 관리가 복잡해질 수 있음

## 토큰 기반 인증
![[Pasted image 20260108024144.png]]
무상태 (state-less) 방식으로, 서버가 사용자의 상태를 저장하지 않음
- 사용자가 로그인하면 서버는 JWT와 같은 토큰을 생성하여 클라이언트에 전달
- 클라이언트는 이후 요청 시 토큰을 포함하여 서버에 전달, 서버는 토큰을 검증하여 사용자의 상태 확인

<장점>
- 서버의 메모리를 절약
- 확장성이 뛰어남
- 모바일 환경에서 유리하고, 다양한 디바이스에서 동일한 방식으로 인증을 처리할 수 있음
<단점>
- 토큰의 유효 기간 관리와 보안 문제를 신중히 고려해야 함

토큰 기반 인증 구현 시 고려사항
1. 토큰의 유효기간을 설정, 만료된 토큰을 처리하는 로직 구현
2. 토큰을 안전하게 저장하기 위해 클라이언트 측에서 보안 조치를 취해야함 예) 모바일앱에서는 안전한 저장소를 사용
3. 리프레시 토큰을 사용하여 엑세스 토큰의 유효기간을 연장하는 방법을 고혀
4. HTTPS를 사용하여 네트워크 상에서의 데이터 전송을 암호화 해야함

### 토큰 저장 방식 

#### local storage / session Storage
브라우저가 요청에 자동으로 안으로 실어줌 -> JS가 직접 헤더에 넣어야 함
문제 :
JS로 접근 가능한 저장소라 `XSS` 한번 터지면 토큰이 그대로 털릴 수 있음
-> 편하지만 XSS 리스크가 커서 보안 관점에서 조심 * [[XSS]]

#### 쿠키
장점 : 브라우저가 자동 전송 + HttpOnly로 JS 접근 차단 가능 -> XSS로 document.cookie에서 못 훔치게 막을 수 있음
단점 :  쿠키는 자동으로 실리니까 `CSRF` 공격면이 생김 
-> SameSite/CSRF 방어를 같이 설계해야 함 *[[CSRF]]
